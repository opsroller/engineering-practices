# Provenance

Provenance is a machine-generated record of how an artifact was built:
the source repository and commit, the build entry point and parameters,
the builder, and the digest of every output. A tool that is part of the
project's build generates it as a Supply-chain Levels for Software
Artifacts (SLSA) provenance file, an in-toto attestation with predicate
type `https://slsa.dev/provenance/v1`. Nobody writes, edits or logs it
by hand.

Examples of generators: `slsa-framework/slsa-github-generator` (writes
`<artifact>.intoto.jsonl`), GitHub's `actions/attest-build-provenance`,
`cosign attest --type slsaprovenance`. Examples of verifiers:
`slsa-verifier`, `gh attestation verify`.

## Steps

1. When onboarding, find the provenance tool in the repository (pipeline
   configuration, build script or task target) and where its output goes.
2. Build anything that ships through the pipeline run that generates the
   provenance, never on a local machine.
3. Don't bypass, disable or edit the provenance step, and don't write or
   edit a provenance file by hand.
4. Before a release is done, check that every artifact has its provenance
   file and that it verifies with the project's verifier.
5. If the project has no provenance tool, or it fails, tell the
   devops-engineer role; its `supply-chain-security` skill sets it up.
   Don't write a substitute.

## Checklist

- [ ] Every shipped artifact came from the pipeline run that generated its provenance
- [ ] Every artifact has a provenance file that verifies
- [ ] Provenance step untouched; no hand-written or edited provenance

## Failure modes

- Shipping a local build, which has no provenance.
- A pipeline change that skips or breaks the provenance step.
- Renaming or repackaging an artifact after the build, so its digest no
  longer matches its provenance.
