# Provenance

Anyone on the team must be able to pick any file in the repository, or
any artifact the project ships, and answer four questions: where did it
come from, how was it made, what went into it, and who changed it. If
they can't, the project can't be rebuilt, audited or trusted.

The pipeline side (build attestations, signing, a software bill of
materials per release) belongs to the devops-engineer role's
`supply-chain-security` skill. This skill is what every role does in its
own work so that record exists.

## What to keep traceable

| What | Traceable when | Record |
|---|---|---|
| A change | It lands as a reviewed, squash-merged pull request with a Conventional Commit title and `Refs: WP-<id>` | Git history (`git-workflow`) |
| A generated file | The generator and the exact command are committed, and the output is regenerated, never hand-edited | Provenance log: "generated by `<script> <args>`" |
| A dependency | It comes through the package manager at an exact version, with the lockfile committed in the same change | Lockfile; additions noted in the pull request |
| A vendored or copied-in file (library, asset, font, data) | Its upstream, exact version or commit, and checksum are recorded, and local changes are separate commits | Provenance log |
| A build artifact | It is built by continuous integration from a commit, never on a local machine, and identified by that commit and its digest | Continuous integration run; release notes |
| A toolchain or pipeline step | It is pinned to an exact version or digest | Manifest or pipeline file |

## Steps

1. Before adding anything that isn't hand-written in this change,
   classify it with the table.
2. Generated output: commit the generator, then the output, and log the
   command. To change the output, change the generator and run it again.
3. Dependencies: add them through the package manager and commit the
   lockfile in the same change. Read what the lockfile diff actually
   adds, transitive packages included.
4. Vendored or copied-in files: add the upstream copy unchanged, with its
   existing headers, in one commit with its log row. Make local changes in
   later commits so the difference from upstream stays visible.
5. Append to the provenance log (`project-onboarding` finds its path):
   path, origin, version or commit, checksum, changes, added in.
6. In the pull request body, list every generated, vendored or
   copied-in item with its origin.
7. Never commit or ship a binary or build output made on a local
   machine. Let continuous integration build it from the commit.

## License headers

Every new file gets the project's license header, never the default a
generator, template or AI tool stamped on it. Check that `LICENSE`,
manifests (`package.json`, `plugin.json`, `Cargo.toml`, ...) and headers
agree. Formats: [license-headers.md](license-headers.md).

## Checklist

- [ ] Every change is a reviewed pull request with a Conventional Commit title and work-package reference
- [ ] Generators and their commands are committed; generated output is not hand-edited
- [ ] Lockfile committed with every dependency change
- [ ] Every vendored or copied-in item has origin, version or commit, and checksum in the log
- [ ] Nothing built on a local machine is committed or shipped
- [ ] Every new file has the project's license header
- [ ] Pull request body lists generated, vendored and copied-in items

## Failure modes

- Hand-editing generated output, so the next regeneration silently
  undoes it.
- Adding a dependency without its lockfile change, so builds resolve
  different versions.
- Vendoring a file and changing it in the same commit, so nobody can see
  what differs from upstream.
- Logging only a URL that later moves or disappears, without the version
  and checksum.
- Shipping a binary built on someone's laptop that no commit can
  reproduce.
- Placeholder files added "temporarily" with no log row, then shipped.
